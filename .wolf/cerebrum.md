- Vapor 4's `FileMiddleware` does NOT serve an index file at `/` by default — `FileMiddleware(publicDirectory:)` alone returns 404 for the directory root; you must pass `defaultFile: "index.html"` explicitly. Caught this live (curl'd `/` and got 404 despite the file existing) rather than assuming it worked from just compiling — worth actually requesting `/` after adding FileMiddleware to any future Vapor app, not just trusting the build.
- SPM `resources: [.copy("Public")]` on an executable target does NOT put files where Vapor's `DirectoryConfiguration.detect()` (plain `getcwd()` + `"Public/"`) looks for them — SPM resource-copy lands files inside a `<target>_<target>.bundle` next to the binary, a different path entirely. For a Vapor app that wants the standard `FileMiddleware(publicDirectory: app.directory.publicDirectory)` convention to work with zero extra code, keep `Public/` as a plain directory at the **package root** (sibling to `Package.swift`/`Sources/`), NOT under `Sources/<target>/` with an SPM `resources:` declaration. Only reach for `resources:`+`Bundle.module` if you explicitly want resources bundled into the binary's output location instead of read relative to the process's working directory.
- Sign in with Apple only ever sends real name/email on the genuine first-ever grant for an Apple ID + Bundle ID/Team combo — this is tracked at the OS/Keychain level, NOT reset by uninstalling the app, clearing local UserDefaults/SwiftData, or even by the app never appearing in Settings > Sign-In & Security > Apps Using Apple ID. Once withheld, the only user-side reset is fully signing out of the Apple ID on the device and back in. Production-correct handling (already implemented in RootView.resolveAccount) is to accept whatever Apple provides and let the user fill in the rest via a manual profile-edit screen — don't expect or debug toward "it should give real data every fresh install," that premise is wrong.

Fixed by adding a private `upsert(_:)` that uses `CKModifyRecordsOperation` with `savePolicy = .changedKeys` (wrapped in `withCheckedThrowingContinuation`) instead of the single-record convenience `save(_:)` — `.changedKeys` always writes the record's fields regardless of whether/how the server copy differs, making every push a true insert-or-update. Applied in both the shared `save(_:)` helper and `pushEventImage`'s separate inline save (the only two CKRecord-save call sites in the file). See [[bug-124]]. **This is the general fix for "why don't my edits to an existing Event/Training/etc. show up on other devices" if that's ever reported again** — check this upsert path before assuming the bug is in a specific feature's own code, since it applies uniformly to every model synced through this file.
